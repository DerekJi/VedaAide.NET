当前评估系统现状分析

1.1 已有的评估框架

VedaAide 已经建立了一个相对完整的评估系统基础，包括：

✅ 已实现的核心组件：
  • Veda.Evaluation 项目：独立的评估模块，包含 EvaluationRunner 和多个 Scorer
  • 三维评分体系：
    • Faithfulness（忠实度）：答案是否仅基于检索上下文，使用 LLM 判断
    • AnswerRelevancy（答案相关性）：答案是否与问题相关，使用 Embedding 相似度
    • ContextRecall（上下文召回）：检索结果是否包含所需信息，使用 Embedding 相似度对比期望答案
  • Golden Dataset 支持：IEvalDatasetRepository 提供 CRUD 操作，支持标准问答对存储
  • 评估报告生成：EvaluationReport 聚合结果并计算整体得分

1.2 当前的不足与改进空间

⚠️ 现有限制：
  • 数据集来源单一：只支持通过 REST API 手动输入 Golden Dataset，没有自动化导入机制
  • 缺少外部数据集集成：不支持从 HuggingFace、Local 或其他开源数据源直接加载
  • 指标体系不够完整：
    • 缺少 Precision@K、Recall@K 等检索层级指标
    • 缺少 BLEU、ROUGE 等文本相似度指标
    • 缺少 F1-Score 综合评估
    • 缺少成本/延迟指标跟踪
  • 无版本管理机制：无法清晰追踪不同版本（模型、prompt、检索策略）的评估对比
  • 缺少自动化评估流程：未集成 CI/CD 评估检查点

1.3 架构优势

✨ 可复用的架构基础：
  • DIP 原则严格实施：所有接口定义在 Veda.Core，实现分散在各层，便于扩展和测试
  • 分层架构清晰：
    • Veda.Core：评估接口定义（IQueryService、IEmbeddingService 等）
    • Veda.Services：检索和生成实现
    • Veda.Evaluation：评分逻辑
    • Veda.Storage：数据持久化
  • 强大的 Mock 支持：已有完整的 unit tests（Veda.Evaluation.Tests），便于集成新功能
  • LLM 路由灵活：LlmRouter 支持多个模型切换，便于交叉模型评估

代码结构修改建议

2.1 当前架构状态

现有架构采用严格的分层设计，整体结构已经很好地支持了 RAG 核心算法与应用层的分离：

查询流程（当前）： API Layer (Veda.Api) ↓ QueryService (Veda.Services) ├→ SemanticEnhancer (查询扩展) ├→ HybridRetriever (检索) ├→ ContextWindowBuilder (上下文构建) ├→ LlmRouter (LLM 路由) └→ HallucinationGuard (幻觉检测) Evaluation Layer (Veda.Evaluation) ├→ FaithfulnessScorer ├→ AnswerRelevancyScorer └→ ContextRecallScorer

2.2 分析：是否需要修改结构？

维度 当前状态 改进建议
核心算法隔离 ✅ 良好。QueryService 封装检索生成逻辑 ⚡ 轻微：提取 RetrieverPipeline 为独立接口
应用层独立性 ✅ 很好。API 层通过接口调用服务 ✅ 无需改动
评估框架集成 ⚠️ 尚可。Evaluation 与 Services 有依赖 🔨 需要：建立 IEvaluationDatasetProvider 接口进行数据解耦
多版本管理 ❌ 无。缺少版本追踪 🔨 需要：IEvalVersionStore 存储评估元数据
数据流独立性 ⚠️ 一般。数据集与 Service 耦合 🔨 需要：IEvalDatasetProvider 统一数据源

2.3 推荐的最小改动方案

🎯 方案：建立"评估数据源"抽象层

核心思路： 不修改现有的 RAG 核心实现，只在 Evaluation 层添加新接口来解耦数据源。

改动点：

  1. 在 Veda.Core 中新增接口：
    // 统一数据源提供接口 public interface IEvalDatasetProvider { Task<IReadOnlyList<EvalQuestion>> LoadAsync( EvalDatasetSource source, // HuggingFace / Local / Database EvalDatasetConfig config, CancellationToken ct = default); } // 数据源配置 public record EvalDatasetConfig { public string? RepoId { get; init; } // huggingface repo public string? LocalPath { get; init; } // local file path public string? Split { get; init; } // "train" / "test" / "validation" public int? MaxRecords { get; init; } }
  2. 在 Veda.Services 中实现多个 Provider：
    • DatabaseEvalDatasetProvider：从 DB 读取（现有逻辑）
    • HuggingFaceEvalDatasetProvider：从 HF 加载并转换
    • LocalFileEvalDatasetProvider：从本地 JSON/CSV 读取
  3. 修改 EvaluationRunner：
    // 改用 public sealed class EvaluationRunner { public async Task<EvaluationReport> RunAsync( IEvalDatasetProvider datasetProvider, EvalDatasetSource source, EvalRunOptions options, CancellationToken ct = default) { var questions = await datasetProvider.LoadAsync(source, options.DatasetConfig, ct); // ... rest of logic remains same } }

优势：

  • ✅ 无侵入性：不改变现有 RAG 查询流程
  • ✅ 高扩展性：支持新数据源无需改动核心代码
  • ✅ 易于测试：Mock IEvalDatasetProvider 即可
  • ✅ 双向兼容：同时支持 DB 和外部数据源

2.4 可选的高级改动：检索管道隔离

（非必须，但长期有益）

如果未来需要独立测试检索算法（不通过 LLM），可考虑：

public interface IRetrieverPipeline { Task<IReadOnlyList<RankedChunk>> RetrieveAsync( string query, RagQueryRequest request, CancellationToken ct = default); } // 重构 QueryService public sealed class QueryService { private readonly IRetrieverPipeline _retrieverPipeline; public async Task<RagQueryResponse> QueryAsync(...) { var candidates = await _retrieverPipeline.RetrieveAsync(...); // ... rest LLM generation logic } }

评估系统功能与指标设计

4.1 评估维度扩展

当前系统的三维评分（Faithfulness、AnswerRelevancy、ContextRecall）已经很好，但需要补充更多维度和粒度指标：

当前维度（保留）

1️⃣ Faithfulness（忠实度）- 0-1

定义： 答案是否仅基于检索上下文，不含虚构信息

方法： LLM 判断（当前实现）或句子级验证

权重建议： 30%

2️⃣ Answer Relevancy（答案相关性）- 0-1

定义： 答案与问题的语义相关性

方法： Embedding 余弦相似度（当前实现）

权重建议： 20%

3️⃣ Context Recall（上下文召回）- 0-1

定义： 检索结果是否包含所需信息

方法： Expected answer vs. Retrieved chunks 相似度（当前实现）

权重建议： 20%

扩展维度（新增）

维度 指标名称 定义 计算方法 权重
检索层 Precision@K Top-K 结果中相关的比例 相关结果数 / K 10%
Recall@K 检索到的相关结果 / 所有相关结果 相关结果数 / 总相关数 10%
NDCG@K 考虑排序的召回（归一化） DCG@K / IDCG@K 5%
生成层 ROUGE-L 答案与期望答案的最长公共子序列比 LCS / (ref_len) 5%
Semantic F1 答案语义的精准度（基于 STS 模型） 2*P*R/(P+R)，P/R 基于 STS 相似度 10%
Token Overlap 答案与期望答案的词汇重叠率 交集词数 / 期望答案词数 5%
效率层 Latency (ms) 端到端查询时间 单位：毫秒 -（跟踪）
Token Cost LLM API 成本 输入输出 token 和×单价 -（跟踪）

4.2 综合评分计算

加权综合评分公式：
Overall Score = 0.30 × Faithfulness + 0.20 × AnswerRelevancy + 0.20 × ContextRecall + 0.10 × Precision@5 + 0.10 × Semantic F1 + 0.05 × NDCG@10 + 0.05 × ROUGE-L 范围：[0, 1]

解读：

  • >0.8： 优秀（生产可用）
  • 0.6-0.8： 良好（需要优化）
  • 0.4-0.6： 一般（有明显问题）
  • <0.4： 差（需要重构）
